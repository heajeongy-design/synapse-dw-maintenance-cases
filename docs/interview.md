# 5분 설명 순서와 예상 질문

## 5분 설명 순서

1. (30초) 대상 시스템: 이미 운영 중인 Synapse + Dedicated SQL Pool + AAS + Power BI 영업 DW. 구축은 타 인력, 유지보수 단독. → [00](00_system_overview.md)
2. (2분) 케이스 1: Refresh OOM → 등급을 더 올리지 않고 뷰 → DIM → STG 로 추적 → 파라미터 이름 불일치 → 수정 후 S1 에서 정상. 재현 결과 표 보여주기.
3. (1분) 케이스 2: 금액 불일치 → Fact 가 아니라 기준정보 누락. 탐지 쿼리.
4. (1분) 케이스 3·4: 입력 품질 편차(스키마 명시), 런타임 변경 대응(인증·책임 이동·경로).
5. (30초) 공통점: 증상 위치 ≠ 원인 위치. 단계마다 "여기는 정상인가"를 쿼리로 확인.

## 예상 질문

**Q. 왜 처음부터 원인을 찾지 않고 Scale-Up 으로 운영했나요?**
A. 담당 전부터 서비스 유지를 위해 쓰던 임시 대응이었다. 같은 테이블에서만 반복되고 규모 대비 메모리가 과도해서 데이터 쪽을 의심했다.

**Q. DIM 이 10~14배인 걸 보고 왜 JOIN 오류가 아니라 적재 문제라고 판단했나요?**
A. 중복 행이 불규칙하지 않고 행 내용이 완전히 같은 복제였다. 그리고 STG 는 전체 건수 = 고유 건수였다. 원천은 정상이고 같은 데이터가 여러 번 들어간 것이므로 STG → DIM 적재 단계를 봤다.

**Q. 파라미터 이름이 틀렸는데 왜 누적이 됐나요?**
A. 전임자가 다른 건을 수정하면서 파라미터 이름을 바꿨고 월별 실행에서 해당 단계가 실패했다. Truncate 가 수행되지 않은 상태에서 적재가 반복되어 누적됐다. 활동 사이 연결 설정까지는 기록해 두지 않았다. 재발 방지로는 실패 시 다음 단계를 멈추는 연결과 적재 직후 키 유일성 검사를 제안했다.

**Q. 비용은 얼마나 줄었나요?**
A. 정확한 절감액은 계산하지 않았다. 원래 Refresh 할 때만 S4 로 올렸기 때문에 월 정가 차이(약 4배)가 그대로 절감액은 아니다. 확실한 효과는 Refresh 마다 하던 수동 Scale-Up/Down 이 없어지고 S1 에서 정상 완료된다는 것이다.

**Q. 같은 문제를 더 빨리 잡으려면?**
A. DIM 적재 직후 키 유일성 검사를 넣으면 첫 번째 잘못된 실행에서 잡힌다(재현에서 확인). 배포 전에 파이프라인 파라미터와 `sys.parameters` 를 비교하면 원인 자체를 막는다.

**Q. 케이스 2 에서 금액 합계는 맞는데 분류만 틀릴 수도 있나요?**
A. 매핑 실패 행이 결과에 남으면 총액은 맞고 분류별 금액만 틀린다. 결과에서 빠지면 총액도 줄어든다. 어느 쪽이든 "원천에는 있고 마스터에는 없는 제품" 쿼리로 찾을 수 있다.

**Q. 스키마를 다 문자열로 두면 문제는 없나요?**
A. 기준정보 컬럼은 계산이 아니라 식별·매핑용이라 문자열이 맞다. 숫자 계산이 필요한 컬럼이면 문자열로 받은 뒤 명시적으로 변환하고, 변환 실패 건수를 검사해야 한다.

**Q. 사례 4 는 실제로 오류가 났나요?**
A. 아니다. 3월 유지보수 중 런타임이 바뀌면 기존 읽기 방식이 문제가 될 수 있다는 걸 알았고, 이후 추가 유지보수 요청 때 오류가 나기 전에 고쳤다.

**Q. 파일 선택을 노트북으로 옮긴 이유는?**
A. 파일을 찾는 책임이 파이프라인에 있으면 노트북 단독으로 실행하거나 테스트할 수 없다. 기능을 새로 만든 게 아니라 위치를 옮긴 것이다.
